1. Problem Statement (PS), Motivation & Scope

1.1 Real-World Motivation

In modern digital society, data breaches occur with alarming regularity. Major institutions—ranging from healthcare providers and credit rating agencies to social networks and utilities—frequently suffer credential leaks. When end users receive notifications that their data has been exposed, they are universally confronted with three systemic failures in existing consumer security tools (such as Have I Been Pwned):

  • Lack of Contextual Severity: Current portals announce that an account appeared in a leak, but provide no objective, weighted calculation of danger. A leaked plaintext password alongside government tax IDs from two months ago is an immediate identity theft emergency; a leaked gaming username from 2012 is low priority. Existing systems treat them identically.
  • Absence of Actionable Guidance: Users are left in a state of anxiety without an ordered, step-by-step remediation plan matched to the specific data attributes compromised.
  • Zero State Tracking: There is no personal task manager or checklist allowing the individual to systematically execute and verify their recovery milestones.

1.2 The Solution: Ledger of Loss

Ledger of Loss is a privacy-first data exposure and recovery navigator. It shifts the paradigm from passive alarmism to structured, measurable remediation:

  1. Verified Ownership Guard: Users register digital identities (email or username) and must confirm ownership before scans are permitted. This is enforced not merely in the UI, but by a database-level trigger (T1) inside PostgreSQL.
  2. Zero-Exposure Cryptographic Scanning: Scans never query plaintext identity values across raw breach dumps. The system hashes the lower-cased identity with SHA-256 and matches it against pre-hashed documents in MongoDB.
  3. Deterministic Database Risk Scoring: Stored procedure calculate_exposure_risk() computes an objective 0–100 risk score based on breach severity base points, recency bonuses (< 24 months), and weights assigned to individual data types.
  4. Actionable Remediation Playbooks: The system maps leaked fields to curated MongoDB playbooks, generating an interactive checklist where users mark actions as completed.
  5. Privacy-Safe Aggregate Analytics: System administrators manage breaches and playbooks, but can only view high-level aggregates (Queries Q2 through Q8). An administrator can never view a user's plaintext identity or personal exposures.

2. System Architecture & Hybrid Data Flow

2.1 Architectural Paradigm & Justification

The project strictly fulfills Option 1: SQL + NoSQL by deploying PostgreSQL 16 alongside MongoDB 7. Each database was chosen based on the mathematical shape and transactional requirements of the data:

Architectural Criterion PostgreSQL 16 (Relational SQL) MongoDB 7 (Document NoSQL)
Primary Role Source of truth for core business entities, user accounts, and transactional workflows. Storage for polymorphic breach records, rich text playbooks, and high-velocity audit logs.
Data Characteristics Highly structured, fixed schema, strict relational dependencies, mathematical computations. Semi-structured, nested arrays, polymorphic key-value metadata, text-heavy guidance.
Transactional Guarantee Full ACID: Atomic scans, foreign keys with ON DELETE CASCADE, triggers. Document-level atomicity, append-only throughput, eventual consistency.
Advanced Features Stored procedures (PL/pgSQL), Triggers T1 & T2, SQL Views, Partial B-Tree Indexes. Strict $jsonSchema engine validation, weighted text search, aggregation pipelines.

2.2 Cross-Database Reference Rule & Compensating Transactions

Crucial Viva Concept: Cross-Database Referential Integrity PostgreSQL and MongoDB cannot share a database-level Foreign Key constraint. Cross-database linkages (such as recovery_actions.playbook_ref storing a MongoDB ObjectId as text, and breach_records.breach_id referencing PostgreSQL breach_id) are managed strictly at the application layer.

When an administrator adds a new breach (involving a relational row in PostgreSQL and hundreds of raw records in MongoDB), the application utilizes a Compensating Transaction Pattern: 

// Cross-Database Pattern in app/api/admin/breaches/route.ts
1. Write master breach to PostgreSQL: INSERT INTO breaches (...) RETURNING breach_id;
2. Attempt bulk write to MongoDB: db.collection('breach_records').insertMany(...);
3. IF MongoDB write throws an error:
     Execute compensating rollback: DELETE FROM breaches WHERE breach_id = createdBreachId;
     Return 500 error: "PostgreSQL row deleted to prevent orphan asymmetric state."
4. ELSE:
     Append audit log entry and commit.

2.3 The ACID Scan Transaction Workflow

The core scanning engine (POST /api/scans) demonstrates strict transactional ordering to ensure optimal latency and atomicity: 

Step 1 [Auth & Guard]: Authenticate user via JWT session. Fetch identity. If verified=false, reject.
Step 2 [Pre-Transaction NoSQL Read]: Outside SQL transaction, compute sha256(identity_value).
      Query MongoDB breach_records for matching hash. Query guidance_playbooks for relevant steps.
Step 3 [ACID PostgreSQL Transaction]:
      BEGIN;
      a) INSERT INTO scan_requests (...) -> Trigger T1 verifies ownership at DB layer.
      b) INSERT INTO exposures (...) ON CONFLICT (identity_id, breach_id) DO NOTHING;
      c) INSERT INTO exposure_data_types (...) -> Maps leaked fields to data_types.
      d) UPDATE exposures SET risk_score = calculate_exposure_risk(exposure_id);
         -> Trigger T2 fires automatically, refreshing user_risk_summary!
      e) INSERT INTO recovery_actions (...) -> Links matched MongoDB playbooks.
      f) UPDATE scan_requests SET status = 'completed', exposures_found = N;
      COMMIT; (On any error -> ROLLBACK; 0 orphan rows persist).
Step 4 [Post-Commit Audit]: Append scan_completed and recommendations_issued to MongoDB audit_logs.

4.2 Normalization Proof (1NF → 2NF → 3NF → BCNF)

First Normal Form (1NF) Compliance

A relation is in 1NF if all domain values are atomic and there are no repeating groups.

  • Every attribute in the schema holds a single atomic scalar value (integers, dates, bounded text, booleans).
  • In earlier unnormalized designs, exposed fields (e.g. "password, financial") were stored as a comma-separated string inside exposures. In our schema, this is decomposed into the relational bridge table exposure_data_types, eliminating all multi-valued attributes.

Second Normal Form (2NF) Compliance

A relation is in 2NF if it is in 1NF and no non-prime attribute depends on part of a candidate key.

  • Tables with single-attribute primary keys (users, identities, breaches, data_types, scan_requests, exposures, recovery_actions, user_risk_summary) are automatically in 2NF because no proper subset of a single-column key exists.
  • The only composite primary key table is exposure_data_types(exposure_id, data_type_id). This table contains zero non-prime attributes; both attributes form the composite key itself. Hence, partial dependency is impossible. Strictly in 2NF.

Third Normal Form (3NF) & BCNF Compliance

A relation is in 3NF if it is in 2NF and has no transitive dependencies. It is in BCNF if for every functional dependency X → Y, X is a superkey.

  • In identities: identity_id determines user_id, identity_value, identity_type, verified. No non-prime attribute determines any other non-prime attribute.
  • In exposures: exposure_id determines identity_id, breach_id, risk_score. Risk score is computed via function and stored directly on the exposure row.
  • In recovery_actions: All non-prime attributes (title, priority, status) are functionally dependent directly on action_id.
  • BCNF Conclusion: In every relation in the relational schema, the left-hand side of every non-trivial functional dependency is a superkey. The database is formally normalized to Boyce-Codd Normal Form (BCNF).

6. Advanced SQL Database Features (ASDL)

6.1 Trigger T1: Guard Against Scans on Unverified Identities

Trigger Timing: BEFORE INSERT ON scan_requests Trigger T1 acts as a gatekeeper. If someone bypasses the web interface and injects a scan request for an identity they do not own or have not confirmed, the database aborts the transaction before any write occurs. 
CREATE OR REPLACE FUNCTION fn_check_identity_verified_before_scan()
RETURNS trigger AS $$
DECLARE
  v_verified boolean;
BEGIN
  SELECT verified INTO v_verified FROM identities WHERE identity_id = NEW.identity_id;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Cannot initiate scan: Identity % does not exist', NEW.identity_id
      USING ERRCODE = '23503';
  END IF;

  IF NOT v_verified THEN
    RAISE EXCEPTION 'Cannot initiate scan: Identity % is not verified by its owner', NEW.identity_id
      USING ERRCODE = 'P0001';
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_scan_requests_verified
BEFORE INSERT ON scan_requests
FOR EACH ROW EXECUTE FUNCTION fn_check_identity_verified_before_scan();

6.2 Trigger T2: Auto-Synchronizing Risk Summaries

Viva Trap: Why does Trigger T2 fire AFTER UPDATE of risk_score? When an exposure row is first inserted, its associated data types do not exist yet in exposure_data_types. Firing on INSERT would calculate risk with zero data types! Therefore, the app inserts the exposure, populates data types, and updates risk_score via calculate_exposure_risk(), which fires Trigger T2 with full data. 
CREATE OR REPLACE FUNCTION fn_refresh_risk_summary_on_exposure_update()
RETURNS trigger AS $$
DECLARE
  v_user_id integer;
BEGIN
  SELECT user_id INTO v_user_id FROM identities WHERE identity_id = NEW.identity_id;
  IF FOUND AND v_user_id IS NOT NULL THEN
    PERFORM refresh_user_risk_summary(v_user_id);
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_exposures_risk_score_update
AFTER UPDATE OF risk_score ON exposures
FOR EACH ROW EXECUTE FUNCTION fn_refresh_risk_summary_on_exposure_update();

6.3 Stored Function: Deterministic Risk Formula

Implements the mathematical formula: Score = min(100, Severity_Base + Sum(Data_Type_Weights) + Recency_Bonus) 

CREATE OR REPLACE FUNCTION calculate_exposure_risk(p_exposure_id integer)
RETURNS integer AS $$
DECLARE
  v_severity text;
  v_breach_date date;
  v_severity_base integer := 0;
  v_recency_bonus integer := 0;
  v_data_type_weight_sum integer := 0;
BEGIN
  -- 1. Fetch breach severity and date
  SELECT b.severity, b.breach_date INTO v_severity, v_breach_date
  FROM exposures e JOIN breaches b ON e.breach_id = b.breach_id
  WHERE e.exposure_id = p_exposure_id;

  -- 2. Severity Base: Low 10, Medium 20, High 30, Critical 40
  CASE v_severity
    WHEN 'low' THEN v_severity_base := 10;
    WHEN 'medium' THEN v_severity_base := 20;
    WHEN 'high' THEN v_severity_base := 30;
    WHEN 'critical' THEN v_severity_base := 40;
    ELSE v_severity_base := 10;
  END CASE;

  -- 3. Recency Bonus: +10 if within past 24 months
  IF v_breach_date >= CURRENT_DATE - INTERVAL '24 months' THEN
    v_recency_bonus := 10;
  END IF;

  -- 4. Sum of exposed data type weights
  SELECT COALESCE(SUM(dt.weight), 0) INTO v_data_type_weight_sum
  FROM exposure_data_types edt JOIN data_types dt ON edt.data_type_id = dt.data_type_id
  WHERE edt.exposure_id = p_exposure_id;

  -- 5. Return bounded score capped at 100
  RETURN LEAST(100, v_severity_base + v_data_type_weight_sum + v_recency_bonus);
END;
$$ LANGUAGE plpgsql STABLE;

6.4 The Consolidated View: user_security_dashboard

CREATE OR REPLACE VIEW user_security_dashboard AS
SELECT
  i.user_id, i.identity_id, i.identity_value, e.exposure_id,
  b.breach_name, b.breach_date, b.severity, e.risk_score,
  risk_level(e.risk_score) AS risk_level, e.discovered_at,
  COALESCE(
    (
      SELECT string_agg(dt.name, ', ' ORDER BY dt.weight DESC)
      FROM exposure_data_types edt JOIN data_types dt ON edt.data_type_id = dt.data_type_id
      WHERE edt.exposure_id = e.exposure_id
    ), 'none'
  ) AS exposed_data_types,
  (
    SELECT COUNT(*)::int FROM recovery_actions ra
    WHERE ra.exposure_id = e.exposure_id AND ra.status = 'pending'
  ) AS pending_recovery_actions_count
FROM exposures e
JOIN identities i ON e.identity_id = i.identity_id
JOIN breaches b ON e.breach_id = b.breach_id;

  b.breach_id, b.breach_name, b.severity, b.breach_date,
  COUNT(e.exposure_id)::int AS total_exposures,
  COALESCE(ROUND(AVG(e.risk_score), 1), 0.0) AS average_risk_score
FROM breaches b LEFT JOIN exposures e ON b.breach_id = e.breach_id
GROUP BY b.breach_id, b.breach_name, b.severity, b.breach_date
ORDER BY total_exposures DESC, average_risk_score DESC;

Q3: HAVING Clause (Privacy-Preserving User Aggregates)

Concept: Filter aggregate groups via HAVING; strictly returns counts, never user PII.

-- File: db/queries/q3_users_high_critical_having.sql
SELECT
  COUNT(*)::int AS users_count_with_multiple_high_critical_exposures,
  COALESCE(AVG(high_crit_exposures), 0.0)::numeric(10, 1) AS avg_high_crit_exposures_per_user
FROM (
  SELECT i.user_id, COUNT(e.exposure_id) AS high_crit_exposures
  FROM identities i JOIN exposures e ON i.identity_id = e.identity_id
  WHERE e.risk_score >= 51
  GROUP BY i.user_id
  HAVING COUNT(e.exposure_id) >= 2
) user_aggregates;

Q4: Non-Correlated Subquery in WHERE Clause

Concept: Dynamic threshold comparison using a scalar subquery.

-- File: db/queries/q4_above_average_risk_subquery.sql
SELECT e.exposure_id, b.breach_name, b.severity, e.risk_score,
  (SELECT ROUND(AVG(risk_score), 1) FROM exposures) AS global_average_risk
FROM exposures e JOIN breaches b ON e.breach_id = b.breach_id
WHERE e.risk_score > (SELECT AVG(risk_score) FROM exposures)
ORDER BY e.risk_score DESC;

Q5: Aggregate Across Many-to-Many Bridge Table

Concept: Evaluating risk exposure distribution per sensitive data type.

-- File: db/queries/q5_data_type_risk_aggregate.sql
SELECT dt.name, dt.weight, COUNT(edt.exposure_id)::int AS occurrences,
  COALESCE(ROUND(AVG(e.risk_score), 1), 0.0) AS average_exposure_risk
FROM data_types dt
LEFT JOIN exposure_data_types edt ON dt.data_type_id = edt.data_type_id
LEFT JOIN exposures e ON edt.exposure_id = e.exposure_id
GROUP BY dt.data_type_id, dt.name, dt.weight
ORDER BY occurrences DESC, dt.weight DESC;

10. 25 Exhaustive Viva Questions & High-Scoring Answers

Q1: Why did you use both PostgreSQL and MongoDB? Why not store everything in PostgreSQL?
Answer: PostgreSQL is the relational source of truth for accounts, identities, scans, and exposures where strict referential integrity (ON DELETE CASCADE), transactional ACID guarantees, triggers, and mathematical stored procedures are required. MongoDB is used for data that is inherently non-relational: 1) breach_records have polymorphic schemas where the extra JSON payload varies per breach source; 2) guidance_playbooks feature nested ordered step arrays and require weighted full-text search ($textScore); and 3) audit_logs represent high-velocity append-only events analyzed using multi-stage aggregation pipelines.
Q2: Why didn't you use an ORM like Prisma or Mongoose?
Answer: An ORM abstracts away the underlying database engine. To demonstrate mastery of database concepts for this course, we used raw SQL migrations in numbered files with the native pg driver using parameterized queries ($1, $2) to prevent SQL injection. In MongoDB, we used the official native driver with database-level $jsonSchema validators rather than Mongoose application schemas.
Q3: How do you maintain foreign keys between PostgreSQL and MongoDB?
Answer: There are no distributed cross-database foreign keys. The databases are loosely coupled at the application layer. For example, recovery_actions.playbook_ref stores a MongoDB ObjectId as a string. When an admin registers a breach across both databases, we implement a Compensating Transaction: PostgreSQL is written first; if the MongoDB write fails, the application deletes the PostgreSQL row to prevent orphan data.
Q4: Explain why Trigger T2 fires on UPDATE OF risk_score rather than on INSERT ON exposures.
Answer: This was a critical timing design decision. When an exposure row is first inserted, its associated data types in the bridge table exposure_data_types have not yet been inserted. If Trigger T2 fired on INSERT, the risk score calculation would see zero data types and calculate an inaccurate score. By firing on AFTER UPDATE OF risk_score, the application first inserts the exposure, populates the data types, and updates the risk score via calculate_exposure_risk(), allowing Trigger T2 to refresh user_risk_summary with complete, accurate data.
Q5: How does Trigger T1 prevent unauthorized scanning?
Answer: Trigger T1 is a BEFORE INSERT trigger on scan_requests. It inspects the target identity row. If verified = false, it raises exception P0001. Because this is executed inside the database engine, even if an attacker bypasses the frontend and sends raw HTTP POST requests or direct SQL inserts, the database strictly refuses to execute the scan.
Q6: How is zero-knowledge / privacy-preserving scanning implemented?
Answer: We never search for plaintext emails or usernames inside MongoDB breach records. The application hashes the lower-cased identity value using crypto.createHash('sha256') and queries MongoDB for matching 64-character hexadecimal digests. The MongoDB collection validator strictly enforces this with the regex '^[a-f0-9]{{64}}$'.
Q7: What is the purpose of the table user_risk_summary if the data can be calculated on the fly?
Answer: It serves as a materialized summary cache for high-frequency dashboard queries. Calculating overall score and counts across multiple joins on every page load causes unnecessary I/O overhead. Trigger T2 and stored function refresh_user_risk_summary() ensure this table is kept 100% synchronized with zero stale data.
Q8: What is a Partial Index and where did you use it?
Answer: A Partial Index indexes only a subset of rows defined by a WHERE predicate. We created CREATE INDEX idx_recovery_actions_pending ON recovery_actions(exposure_id) WHERE status = 'pending'. Since users quickly complete or dismiss tasks, the vast majority of historical actions are completed. The partial index stays compact in memory and accelerates open task lookups.
Q9: What happens when an identity is deleted? How is data consistency maintained?
Answer: The foreign key constraint on exposures.identity_id and scan_requests.identity_id specifies ON DELETE CASCADE. Deleting an identity automatically cascades and deletes all associated exposures, data type links, and recovery actions. Within the same transaction, the application executes SELECT refresh_user_risk_summary(user_id) to recalculate the user's score to reflect the deletion.
Q10: Why did you use ON CONFLICT DO NOTHING in exposures?
Answer: To ensure idempotency during re-scans. The table enforces UNIQUE (identity_id, breach_id). If a user scans their identity multiple times, ON CONFLICT DO NOTHING ignores already discovered breaches, preventing duplicate exposure rows while recording the new scan in scan_requests.
Q11: How does MongoDB enforce schema validation?
Answer: Using the $jsonSchema operator passed to db.createCollection() with validationLevel: "strict" and validationAction: "error". It validates BSON data types, required fields, regular expressions, and sets additionalProperties: false to prevent unauthorized fields from being injected.
Q12: Explain Query Q3 and why it uses the HAVING clause.
Answer: Query Q3 identifies high-risk users who have at least 2 exposures with a risk score ≥ 51. Because the condition COUNT(e.exposure_id) >= 2 applies to an aggregate grouping (per user), it cannot be evaluated in a WHERE clause and must be placed in HAVING. Furthermore, the query wraps this in an outer count, returning strictly aggregate numbers to preserve user privacy.
Q13: What is the difference between a function and a stored procedure in PostgreSQL?
Answer: A stored function returns a value and can be called directly inside SELECT statements or triggers (e.g. calculate_exposure_risk() returns integer). A procedure (created with CREATE PROCEDURE) does not return a value and is invoked using CALL, allowing transaction control (COMMIT/ROLLBACK) inside the procedure body.
Q14: How is password security implemented?
Answer: Passwords are never stored in plaintext. They are hashed using bcryptjs with a salt work factor of 10 rounds. Bcrypt incorporates a cryptographic salt and is resistant to rainbow table attacks and brute force.
Q15: Explain the mathematical risk calculation formula.
Answer: Score = LEAST(100, severity_base + SUM(weights) + recency_bonus). Base points: Low = 10, Medium = 20, High = 30, Critical = 40. Recency bonus is +10 if the breach occurred within the last 24 months. Sensitive data types contribute weighted points (password = 30, financial = 25, government ID = 25, phone = 10, etc.). The final sum is capped at 100.
Q16: What is the purpose of string_agg in view user_security_dashboard?
Answer: string_agg(dt.name, ', ' ORDER BY dt.weight DESC) is an aggregate function that collapses the multiple data types linked to an exposure into a single comma-separated string, ordered by priority, allowing the frontend to render the exposure row without a nested query loop.
Q17: How does Next.js middleware protect admin routes?
Answer: The file middleware.ts intercepts all requests matching /admin/:path* and /api/admin/:path*. It reads the session cookie, verifies the cryptographic signature with jose, and inspects the role claim. If the role is not 'admin', it immediately bounces the user to /dashboard or returns HTTP 403 Forbidden.
Q18: What does the term "idempotent" mean in the context of your scan transaction?
Answer: Idempotency means that running the operation multiple times produces the same result without unintended side effects. Because we use ON CONFLICT (identity_id, breach_id) DO NOTHING, repeatedly scanning an identity will not create duplicate exposures or duplicate recovery actions.
Q19: What is the difference between 2NF and 3NF?
Answer: 2NF eliminates partial functional dependencies (where a non-key attribute depends on only part of a composite key). 3NF eliminates transitive functional dependencies (where a non-key attribute depends on another non-key attribute). Our schema satisfies both.
Q20: How does MongoDB full-text search work with textScore?
Answer: MongoDB indexes words from designated fields and removes language stop words. In our compound text index, we assigned weights: title (10), summary (5), tags (5), steps (1). When querying with $text: {{ $search: "query" }}, MongoDB calculates a relevance score (textScore), allowing results to be sorted so the most relevant playbooks appear first.
Q21: What is a multikey index in MongoDB?
Answer: When an index is created on a field that holds an array (such as applies_to.data_types), MongoDB creates index keys for every single element in the array. This allows instant lookups when checking whether a breach's exposed fields match a playbook's applicable categories.
Q22: How do you prove that an ACID transaction rolled back cleanly?
Answer: In our automated test tests/scans/test_scan_transaction.ts, we inject an intentional foreign key violation during the scan transaction after scan_requests and exposures have been written. We catch the exception, execute ROLLBACK, and query the database to verify that exactly 0 scan rows and 0 exposure rows persist.
Q23: What is the difference between authentication and authorization in your app?
Answer: Authentication verifies identity (e.g. logging in with email and password via /api/auth/login and issuing a signed JWT). Authorization determines permissions (e.g. checking whether user.role === 'admin' before allowing access to breach catalogs or audit trails).
Q24: Why are credentials kept only in environment variables?
Answer: Hardcoding database connection strings, passwords, or JWT secrets in source code creates severe security vulnerabilities and violates 12-factor application guidelines. All credentials reside in .env, which is excluded from version control via .gitignore, with a template provided in .env.example.
Q25: How did you divide the work between both teammates?
Answer: Rather than a superficial split where one member only does UI and one only does database, we divided the work into two full vertical slices: Teammate A handled Slice A (the relational PostgreSQL schema, DDL migrations, Triggers T1 & T2, stored functions, the ACID scan transaction route, and the exposure detail UI). Teammate B handled Slice B (the MongoDB NoSQL schemas, $jsonSchema validators, JWT/bcryptjs authentication, middleware, dashboard views, admin analytics Q2–Q8, and documentation). Both members contributed to database design and application code.
